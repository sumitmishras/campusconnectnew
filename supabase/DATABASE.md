# Campus Connect — Database Design

Postgres 15+ on Supabase. Designed to run a single campus of a few thousand
students on the free/small tier and to reach several lakh students without a
schema rewrite — only bigger hardware and, eventually, a read replica.

Migrations live in `supabase/migrations/` and are numbered in dependency
order. Run them top to bottom.

| File | Contents |
|---|---|
| `0001_extensions_and_types.sql` | Extensions, UUIDv7, all enums, shared triggers |
| `0002_identity_and_profiles.sql` | Universities, programs, profiles, presence, badges, devices |
| `0003_social_graph.sql` | Connections, blocks, profile views |
| `0004_chat.sql` | Conversations, members, messages, attachments |
| `0005_campus_hub.sql` | Communities, clubs, study groups, events, projects, polls |
| `0006_notifications_and_moderation.sql` | Notifications, reports, rate limits, audit |
| `0007_chat_functions.sql` | `send_message`, `mark_read`, chat list, pagination, group creation |
| `0008_rls_policies.sql` | Row Level Security across every table |
| `0009_storage.sql` | Buckets and storage policies for photos/documents |
| `0010_jobs_and_maintenance.sql` | Fan-out, retention, presence decay, cron |
| `0011_seed_reference_data.sql` | CU programs, badges, tags, department communities |
| `0012_app_integration.sql` | Project covers, `clear_my_history`, `clear_my_notifications`, `create_poll`, Realtime for polls/events |

## The chat system

This is the part that has to hold up, so the reasoning is spelled out.

### One table for DMs and groups

`conversations` has a `type` of `direct` or `group`. A DM is just a group with
two members plus a `direct_key` (`"<lower uuid>:<higher uuid>"`) that a unique
index uses to stop duplicate threads when two devices race.

Group conversations carry `source_type` + `source_id` pointing at the club,
community, study group or project they belong to — which is exactly what
`chat_model.dart` already assumes ("Its `id` is the id of that
community/club/group, so joining and leaving stay in sync").

The payoff: `conversation_members` is *also* the membership table for clubs,
communities and study groups. Joining a club and appearing in its chat are one
INSERT, so they cannot drift apart. Four join tables collapse into one.

### `seq`, not timestamps

Every message gets a per-conversation `seq bigint`, allocated inside
`send_message()` by `UPDATE conversations SET last_seq = last_seq + 1 …
RETURNING last_seq`. That UPDATE takes a row lock, which serialises concurrent
sends in that one thread — so `seq` can never duplicate or reorder. Different
conversations never contend with each other.

What this buys:

- **Unread count** is `conversations.last_seq - conversation_members.last_read_seq`.
  Pure arithmetic on two columns already in memory. No counter table to drift,
  no `COUNT(*)` over messages, no per-message receipt rows.
- **Read receipts** are one integer per member. The blue tick in a DM is "the
  other member's `last_read_seq >= my message's seq`". The group "seen by all"
  is `MIN(last_read_seq)` over the other members. Compare that to a receipts
  table, where one message to a 200-person club thread writes 200 rows.
- **Pagination** is a keyset scan: `WHERE conversation_id = $1 AND seq < $cursor
  ORDER BY seq DESC LIMIT 40`. Constant cost no matter how far back you scroll,
  unlike `OFFSET`, which re-walks every row it skips.

Timestamps are still stored, but they are for display. Ordering never depends
on them — phone clocks are wrong, and two messages in the same millisecond
would tie.

### Partitioning: hash on `conversation_id`

`messages` is `PARTITION BY HASH (conversation_id)` into 16 partitions, with
the primary key `(conversation_id, seq)`.

The reflex is to partition a large append-only table by time. That is wrong
here. Every read in a chat app is "the last N messages of conversation X", and
the pagination cursor is `seq`, which tells the planner nothing about
`created_at` — so a time-partitioned table would have to probe the index of
*every* partition on every history load. Hashing on `conversation_id` prunes
each read to exactly one partition.

Retention is the one thing time partitioning wins at, and that runs as a
background job at 3am where the extra cost does not matter. A BRIN index on
`created_at` (a few KB, because v7 ids keep insert order aligned with physical
order) covers those range deletes.

`message_attachments` and `message_reactions` are hashed the same way on the
same key, so their foreign keys stay inside a single partition and the "Media &
Documents" tab prunes too.

16 is not adjustable later without a rewrite, hence the generous choice up
front. At 500 M messages that is ~31 M rows per partition — comfortable.

### Idempotent sends

`messages.client_msg_id` is generated by the app *before* the first send
attempt and reused on every retry. `UNIQUE (conversation_id, client_msg_id)`
plus an early lookup in `send_message()` means a dropped response over campus
wifi returns the original message instead of posting a duplicate bubble.

### What is deliberately *not* in the database

- **Typing indicators.** Valid for three seconds. Writing them to Postgres
  generates more traffic than the messages themselves. Keep them in the chat
  server's memory / Redis pub-sub.
- **Online status.** `user_presence` exists as the durable fallback, but the
  live write path should be Redis with a periodic flush. Note that
  `user_presence` is a separate narrow table with `fillfactor = 70` and **no
  secondary indexes** — putting `is_online` on `profiles` would rewrite a wide
  row carrying five GIN indexes and a generated `tsvector` on every heartbeat.
  That single mistake is the fastest way to kill this database at 100k users.
- **Per-message read receipts.** See `seq` above.

## Photos and documents

Bytes go to Supabase Storage; the database holds metadata and does the
authorisation. Three steps:

**1. Ticket.** The client calls `create_upload_ticket(conversation_id, kind,
file_name, mime_type, size_bytes)`. This validates membership, size (5 MB, matching
`AttachmentService.maxBytes`) and rate limit, then returns a **server-generated**
object path:

```
chat-media/{conversation_id}/{sender_id}/{uuid}.{ext}
```

The path is server-chosen so a client cannot overwrite another thread's object
by supplying its own key.

**2. Upload.** The client PUTs to that path. The storage INSERT policy
(`cc_chat_media_write`) allows it *only* if a live, unconsumed ticket exists for
that exact path and user. No ticket, no upload.

**3. Send.** `send_message(..., p_kind => 'photo', p_attachments => '[{"object_path": "...", "width": …}]')`
looks the ticket up again, copies the trustworthy fields (kind, size, mime,
filename) **from the ticket, not from the client payload**, creates the
`message_attachments` row and marks the ticket consumed — all in the same
transaction as the message.

Anything the client could lie about comes from the ticket. Anything harmless
(dimensions, blurhash, page count) comes from the payload.

### Why `chat-media` is private

A public bucket with unguessable names is not access control. Anyone who ever
receives a URL keeps it forever, including after being removed from the group.
The read policy checks conversation membership live, so removing someone cuts
off every file ever shared in that thread instantly. Clients get files through
short-lived signed URLs.

`avatars` *is* public, because Discover renders forty of them per scroll and
signing each one would be forty round-trips.

### Orphan cleanup

An upload with no message pointing at it — someone opened the picker and backed
out — would otherwise sit in the bucket forever. `cleanup_orphaned_uploads()`
returns the expired unconsumed paths; the caller deletes them from Storage
(SQL cannot delete bytes out of a bucket).

### Malware

`message_attachments.scan_status` starts `pending`. A worker reads the queue
(`attachments_scan_queue_idx`), scans, and sets `clean` / `infected`. The client
should not offer a download until `clean`. Not wiring a scanner is a decision,
not an oversight — make it consciously.

## Security model

With Supabase the Flutter app talks to Postgres over PostgREST using the
student's own JWT. **RLS is not defence in depth here — it is the entire
authorisation layer.** Anything without a policy is reachable by anyone who
pulls the anon key out of the APK.

Every policy in `0008` starts from "nothing is visible" and adds back only what
that student is entitled to.

Three things worth pointing out:

**Column-level grants where RLS cannot reach.** RLS decides which *rows* you can
touch, never which *columns*. `trust_level`, `verification_level`,
`report_count` and `strike_count` are set by triggers and back-office code, so
`UPDATE` is revoked on `profiles` and re-granted column by column. Same pattern
on `conversation_members` (you may move your read pointer, not your role) and
`notifications` (you may set `read_at`, nothing else).

**The rate limiter has two front doors.** `check_rate_limit(p_user, …)` takes an
arbitrary user id, so it is service-role only — exposed to clients, anyone could
burn through another student's quota. RLS policy expressions run with the
*caller's* privileges, so policies use `check_my_rate_limit(...)`, which closes
the user to `auth.uid()`.

**State machines live in triggers, not `WITH CHECK`.** A `WITH CHECK` clause
cannot express "only the addressee may set `state = 'accepted'`", because it
cannot see the old row. `tg_connection_transition` does, and rejects a requester
trying to accept their own request.

Blocks are enforced at every layer: Discover filtering, DM creation, *and* every
send (`send_message` re-checks, so blocking or disconnecting makes the thread
read-only immediately rather than at next app launch).

## Scaling

Where the numbers land at roughly 1 lakh students, half of them active daily:

| | Rows/year | Notes |
|---|---|---|
| `profiles` | 100 k total | Trivial |
| `messages` | ~1.8 B at 100 msg/user/day | The one that matters |
| `message_attachments` | ~90 M | ~5% of messages |
| `notifications` | ~500 M | 60-day retention keeps it ~80 M live |
| `conversation_members` | ~5 M | ~50 threads per student |

What holds and what to do, in the order you will need it:

1. **Connection pooling.** Supabase's pooler (Supavisor) in transaction mode.
   Postgres dies of too many connections long before too much data. Do this
   first, on day one.
2. **The chat server holds the websockets, not Postgres.** One Node process
   handles tens of thousands of sockets; each Postgres connection costs ~10 MB.
   Never map sockets to connections.
3. **Read replica** for Discover, the events feed and profile reads once the
   primary's CPU passes ~60%. Chat stays on the primary — replica lag would show
   up as messages arriving out of order.
4. **Redis** for presence, typing, and the real rate limiter. `user_presence`
   and `rate_limits` in Postgres are the durable backstop, not the hot path.
5. **Archive old messages** past two years to cold storage via the BRIN index.
   Only when you actually need the disk.

The schema itself does not change at any of these steps. That is the point.

### Indexes that matter most

- `messages` PK `(conversation_id, seq)` — every history read.
- `conversation_members_user_idx` — the chat list.
- `conversation_members_fanout_idx` — covering, so the send path reads
  recipients without touching the heap.
- `profiles_discover_idx` + the two GIN indexes on `interests` / `looking_for`
  — Discover.
- `notifications_unread_idx` — partial, so it stays tiny.

Every high-traffic index is **partial** (`WHERE deleted_at IS NULL`,
`WHERE left_at IS NULL`, `WHERE read_at IS NULL`). Rows that can never be
returned should not occupy index pages.

### Denormalised counters

`member_count`, `going_count`, `vote_count`, `applicant_count`,
`last_message_preview` are maintained by triggers. The events screen shows
"142 going" on every card; counting rows per card would be the single most
expensive query in the app. Triggers keep them correct without the app having
to remember.

## The Node + TypeScript chat server

Supabase Realtime alone can carry the app to a few thousand users. Past that,
and for anything needing custom presence, typing or fan-out control, put a Node
gateway in front. Suggested shape:

```
Flutter ──ws──► Node gateway ──► Postgres (send_message RPC)
   │                 │
   │                 ├──► Redis (presence, typing, socket routing)
   │                 └──► FCM (push for offline members)
   └──https──► Supabase Storage (signed upload/download)
```

Responsibilities split like this:

- **Postgres** owns durability, ordering (`seq`) and authorisation.
- **Node** owns the socket layer and fan-out to *connected* members.
- **Redis** owns everything ephemeral, plus which gateway node holds which
  socket (`user_presence.node_id` mirrors this for debugging).
- **FCM** gets the rest, driven by `fanout_message_notifications()`.

The send path:

1. Socket receives `{conversationId, clientMsgId, body, attachments}`.
2. Call `send_message(...)` with the *user's* JWT, so RLS and the block checks
   still apply. Never the service key on a user-initiated path.
3. Emit the returned row to every connected member (`conversation_members`,
   `left_at IS NULL`).
4. **After** the transaction commits, call `fanout_message_notifications()` and
   push to members who were not connected.

Step 4 is a separate call, not a trigger, on purpose — see the comment at the
top of `0010`. Inside the transaction, a message to a 500-member club would do
500 inserts while still holding the `conversations` row lock, throttling the
whole thread behind its own notifications.

Recommended packages: `ws` (lighter than Socket.IO if you control both ends),
`@supabase/supabase-js`, `ioredis`, `zod` for payload validation,
`firebase-admin` for push.

## Wiring the Flutter app up

### How the switch works

Credentials come from `--dart-define`, never from source control:

```bash
flutter run \
  --dart-define=SUPABASE_URL=https://xxxx.supabase.co \
  --dart-define=SUPABASE_ANON_KEY=eyJhbGci...
```

With them absent the app runs entirely on mock data, exactly as before
(`AppConfig.useSupabase`). That is what lets the migration happen one module at
a time without the app ever being unrunnable — and it keeps the repo clonable
by someone with no project of their own.

### Progress

| Module | Status |
|---|---|
| **Auth** | Done — `AuthProvider` delegates to `SupabaseAuthBackend` or `MockAuthBackend` |
| **Profiles** | Done — `ProfileRepository`, badges, presence, privacy, completion |
| **Connections / Discover** | Done — `ConnectionRepository`, `DiscoverRepository`, keyset paging, blocks, reports |
| **Campus Hub** | Done — `CampusRepository`: events + RSVPs, communities, clubs, study groups, projects + applications, polls + votes, notifications |
| **Chat** | Done — `ChatRepository`: `get_chat_list()`, `get_messages()`, `send_message()`, `mark_read()`, `delete_message()`, `join_group()` / `leave_group()` |
| **Storage** | Done — `StorageRepository`: avatars, chat photos and documents, campus assets |
| **Realtime** | Done — messages, notifications, polls, events (Postgres changes); typing and presence (broadcast / presence channels) |
| Reference data | Done — `ReferenceRepository` reads `programs` and `tags`; the Dart option lists are the fallback only |

The data layer is assembled in `lib/core/data/repositories/repositories.dart`.
One place reads `SupabaseService.isReady` and hands out either the Supabase or
the mock implementation, so no provider holds a `SupabaseClient` and no screen
knows which mode it is in. `Repositories.overrideForTest` / `reset` are the
test seam — call `reset()` in `setUp`, or a signed-in mock profile leaks into
the next test.

`MockDataGenerator` is now reachable from exactly one layer: the `Mock*`
repositories. Nothing in `lib/core/providers/` or `lib/features/` imports it.
That is what keeps "run with no credentials" working without any screen knowing
about it.

### What the app subscribes to

| Channel | Carries | Why not the other way |
|---|---|---|
| `cc-inbox` (postgres_changes on `messages`) | Every message in a thread the student belongs to | RLS scopes it, so no per-conversation filter is needed or correct — the set of threads changes as they join things |
| `cc-campus` (postgres_changes) | Own `notifications`, `poll_options`, `polls`, `events` | The provider re-reads the affected list rather than patching a replicated row, so a tally and its "have I voted" flag cannot disagree |
| `cc-typing-<conversation>` (broadcast) | Typing indicators | Valid for ~3 seconds; writing them to Postgres would out-traffic the messages |
| `cc-presence` (presence) | Who is online right now | A phone that loses signal never writes a disconnect; leaving the channel *is* the event |

A message arriving over Realtime is re-read through `get_messages()` for that
one `seq` before it reaches the UI. The replicated row carries neither the
sender's name nor its attachment rows, and a group bubble needs both.

### What Auth looks like now

- `lib/core/config/app_config.dart` — the `--dart-define` switch.
- `lib/core/services/supabase_service.dart` — client init; a no-op in mock mode.
- `lib/core/services/auth_backend.dart` — the seam. `AuthBackend` with two
  implementations; the screens never know which is live.
- `lib/core/data/profile_mapper.dart` — `profiles` row ⇄ `User`, and the
  allow-list of writable columns.
- `lib/core/providers/auth_provider.dart` — the state machine, unchanged in its
  public API so no screen needed rewriting.

Sign-in is Supabase email OTP against `@cuchd.in`. The `on_auth_user_created`
trigger creates the profile shell and parses the university id in the same
transaction, so there is never an auth row without a profile. `CuIdentity` still
runs client-side, but only to validate before a request is sent.

`onboarding_completed_at` is what distinguishes a shell from a finished
profile, and therefore what routes between the registration wizard and the app.

Three things changed in the app while doing this:

- **Enums now serialise by name.** `user_model.dart` used `.index`; Postgres
  enums are text on the wire, and ordinals would silently reinterpret every
  stored row if a value were ever inserted mid-enum. `TrustLevelWire` /
  `VerificationLevelWire` handle it, and still accept the old ordinals so a
  profile cached by an earlier build keeps loading.
- **The OTP screen is length-aware.** Supabase sends six digits, the mock four.
  The demo banner only renders in mock mode.
- **Department, course and year are no longer editable.** They are derived —
  department and course from the programme code in the university id, year from
  the admission year every July — and the column grants would have rejected the
  write anyway. The edit screen shows them read-only with an explanation.

### How Chat maps

`Chat.otherUser` holds a full `User`. `get_chat_list()` flattens the other
student's name, avatar and presence into the row, and the chat list then does
one batched `profiles` read for the DM counterparts so tapping through to a
profile has something to show. Two round trips for the whole tab, not N+1.

Names map cleanly: `User.uid` → `profiles.university_uid`, `User.name` →
`full_name`, `User.profilePhotoUrl` → `avatar_url`, `Message.isSeen` ←
`get_messages().seen_by_all` (which *is* `seq <= MIN(other members'
last_read_seq)`), `Attachment.previewUrl` ← a signed URL built from
`object_path`, one request per page rather than per bubble.

Two model fields exist purely to keep the screens from having to know any of
this: `Message.isMine` is resolved when the row is mapped (the id is a uuid
against Supabase and `'me'` in mock mode), and `GroupChat.conversationId` sits
beside `GroupChat.id` because `conversations.source_id` is the club and
`conversations.id` is the thread — screens navigate by the first, every RPC
takes the second.

`User.year` is the one that does not map to a column, on purpose:
`admission_year` is stored (a fact that never changes) and the year of study is
derived (`public.study_year()`), because it rolls over every July without anyone
touching the row. To filter Discover by "3rd Year", convert with
`admission_year_for_study_year()` so the query hits the index.

## The RPC surface

Everything the app should call instead of writing tables directly:

| Function | Purpose |
|---|---|
| `get_or_create_direct_conversation(other_user)` | Open a DM. Race-safe. |
| `send_message(conversation_id, body, kind, client_msg_id, reply_to_id, attachments, mentions)` | The only write path into `messages`. |
| `create_upload_ticket(conversation_id, kind, file_name, mime_type, size_bytes)` | Step 1 of sharing a photo/document. |
| `mark_read(conversation_id, seq)` | Advance the read pointer; returns remaining unread. |
| `get_chat_list(limit, before)` | The whole Chats tab in one query. |
| `get_messages(conversation_id, before_seq, limit)` | Keyset-paginated history with attachments as JSON. |
| `total_unread()` | Tab-bar badge. |
| `delete_message(conversation_id, message_id)` | Soft delete. |
| `join_group(conversation_id)` / `leave_group(conversation_id)` | Covers clubs, communities, study groups, project teams. |
| `create_study_group(subject, title, …)` | Group + thread + host membership, atomically. |
| `clear_my_history(conversation_id)` | "Clear messages" — moves this student's `visible_from_seq` only. |
| `clear_my_notifications()` | "Clear all" — DELETE is revoked on `notifications`. |
| `create_poll(question, options, …)` | Poll + its options, atomically. |

Direct table access from the client is read-mostly by design: `messages`,
`message_attachments`, `upload_tickets`, `notifications` and
`moderation_actions` have their INSERT/UPDATE/DELETE privileges revoked
outright. If a new write path is needed, it should be a function, not a policy.

## Verification status

All 11 migrations were executed against **PostgreSQL 16.4** and the suite in
`supabase/tests/` was run against the result: **150 assertions, 150 passing.**
See `tests/README.md` to reproduce.

This was a local Postgres with a compatibility shim
(`tests/00_local_supabase_shim.sql`) standing in for Supabase's `auth`,
`storage`, roles and publication. Everything the migrations touch is real; what
is simulated is the surrounding platform. Still to confirm on a live project:
Auth's own OTP flow, Storage actually moving bytes, and Realtime end-to-end.

Six bugs were found by running it, all now fixed. Five of them could not have
been caught by reading the SQL:

1. **RLS does not inherit to partitions.** `ENABLE ROW LEVEL SECURITY` on
   `public.messages` sets the flag on the parent only. PostgREST exposes every
   table in `public`, so `messages_p3` was its own unauthenticated endpoint. An
   outsider read 0 rows from `public.messages` and **all 39** from the
   partitions. Fixed by enabling RLS on every partition (no policies = deny
   direct access; the parent's policies still govern normal reads). Any
   partition added later must do the same — section 18 of the suite enforces it.

2. **Realtime published under partition names.** With
   `publish_via_partition_root` off, changes were announced as `messages_p7`,
   so a client subscribed to `public:messages` would have received nothing.
   The whole chat UI would have looked broken with no error anywhere.

3. **Blocking a connected student failed outright.** The block trigger cancels
   the connection, but the state-machine guard rejected every transition out of
   `accepted` — so the INSERT into `blocks` aborted. Blocking was broken in
   exactly the case it matters most.

4. **`ON CONFLICT (direct_key)`** could not infer a *partial* unique index, so
   opening any DM raised. The index predicate has to be repeated in the clause.

5. **A unique index on a partitioned table must contain the partition key** —
   `message_attachments (bucket, object_path)` was rejected at create time.

6. **`now()` in an index predicate** — index predicates must be IMMUTABLE, and
   `moderation_active_idx` used `WHERE expires_at > now()`.

Before pushing to a real project, re-run the suite there (`tests/README.md`),
then check the three platform pieces the shim cannot cover: sign in with a real
`@cuchd.in` address, upload an actual file to `chat-media` and confirm a
non-member gets 403 on the signed URL, and open two clients to confirm a message
arrives over Realtime.

## Setup

```bash
npx supabase init
npx supabase link --project-ref <your-ref>
npx supabase db push
```

Then, in the dashboard:

- **Database → Extensions** → enable `pg_cron`, and re-run `0010` so the jobs
  register (the migration skips them with a notice if it is off).
- **Auth → Providers → Email** → enable OTP; set the redirect/deep link.
- **Auth → URL Configuration** → restrict sign-ups to `cuchd.in` (the
  `on_auth_user_created` trigger also rejects other domains, but rejecting at
  the edge is cheaper).

For local work, `npx supabase start` runs the whole stack in Docker.

### Verify RLS is actually on

Worth doing once before launch — this should return zero rows:

```sql
select tablename from pg_tables t
where schemaname = 'public'
  and not exists (
    select 1 from pg_class c
    where c.relname = t.tablename and c.relrowsecurity
  );
```
